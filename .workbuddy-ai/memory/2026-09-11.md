## CLI `--download-video <codec>` was completely broken (NameError)

Found by adding the first tests for `translate._video_selector_for`. It
referenced a bare `youtube_media`, but `translate.py` has **no module-level**
import of it — the only import is function-scoped inside
`_download_youtube_media` (`from src import youtube_media`, ~line 738). A local
import does not make the name visible to a *different* function, so every call
raised:

```
NameError: name 'youtube_media' is not defined
```

This is **pre-existing** (the `git diff` shows the original line was already
`youtube_media.resolve_video_option(...)`); my change only replaced the trailing
`return "bv*+ba/b"`. `_download_youtube_media` catches `RuntimeError` only, so a
`NameError` escaped as a traceback — the CLI could not download a video at all.

Fix: local `from src import youtube_media` inside `_video_selector_for`, matching
the module's lazy-import style.

### Live re-check against a real video

| choice | selector |
|---|---|
| `best` | `bv*+ba/b` |
| `av1` | `401+bestaudio/…` (2160p) |
| `vp9` | `628+bestaudio/…` (2160p) |
| `h264` | `312+bestaudio/…` (**1080p** — does not borrow the 2160p stream) |
| `h264` with the family removed | `RuntimeError: This video is not available in H.264: no H.264 stream was found.` |

New `TestCliVideoSelector` (11 tests) covers pinning, no cross-codec borrowing,
the refusal path, and that every CLI `choices` value resolves. Suite: **544 passed**.

### Lesson
A function-scoped `import` is invisible to every other function in the module.
If a helper references a name, the import has to live in the helper (or at
module level) — tests calling the helper directly catch this immediately, which
is exactly why the untested CLI path rotted.

## Packaged-build ffmpeg naming — verified (it was already correct)

Every selector the UI offers is a **merge** (`video-id + bestaudio`), so the
packaged app cannot download anything without a working ffmpeg. `build_exe.bat`
bundles imageio's `ffmpeg-win-x86_64-v7.1.exe`, but yt-dlp's
`--ffmpeg-location` only finds a binary *literally* named `ffmpeg(.exe)` when
scanning a directory — so `_ensure_ffmpeg_exe_named()` copies it to
`ffmpeg.exe` (into temp when the frozen bundle is read-only). Without it the
merge silently never runs and the user gets a video-only file plus a stray
audio file.

Exercised against the **real** bundled binary: rename → `ffmpeg.exe`, same
size, idempotent, original left in place, read-only dir → temp fallback. All
correct — **no bug here**, but it had no test coverage, so it now has 8
(`TestPackagedFfmpegNaming`), including stale-copy refresh and graceful
degradation when the copy fails.

Note the `.spec` pins one absolute path to the build machine's
site-packages; that is fine for a local single-machine build but would break on
another machine (consider `imageio_ffmpeg.get_ffmpeg_exe()` in `build_exe.bat`,
which already resolves it dynamically).

## Corrected an earlier mis-read: the .spec is generated, not the build input

Follow-up on the note above — I originally assumed the spec was the source of
truth for the build. It is not. `build_exe.bat` calls `python -m PyInstaller`
with **explicit CLI flags** and never passes the spec; PyInstaller then writes
the effective config back out to `TranslationAgent.spec`, which is why the
committed copy holds absolute `C:\Users\Njoro\...` paths. **The build is already
portable** as long as you run `build_exe.bat` (it resolves PySide6 and ffmpeg
with `python -c` at build time).

Documented rather than "fixed": a `GENERATED FILE — do not hand-edit` header on
the spec (guarded with `ast.parse` to be sure it still loads) and a "Known
limitation" section in `AGENT_DOCUMENTATION.md`. Deliberately did **not**
hand-edit the absolute paths — the next build overwrites the file, so that
would be churn that appears useful but changes nothing.

Also documented the deliberate `openai` / `dotenv` module-level imports in
`translate.py`: they are PyInstaller collection hooks (`src/translate.py`
imports `openai` lazily), so pyflakes' "imported but unused" is expected there.
Noted so a future cleanup pass doesn't delete them and silently break the
packaged build.

### Lesson
A committed file is not necessarily a build *input* just because it describes
the build. Read the build script first; "fixing" a generated file is wasted
work.

## Closed the last gap: build contract is now tested (`tests/test_build_contract.py`)

A full PyInstaller run is too heavy for the suite, but almost everything that
breaks a frozen build is a *declaration* problem — cheap to verify. The 11 tests
parse the real `build_exe.bat` and assert:

- every `if not exist` guarded path (vendor binaries) and every
  `--add-data` / `--add-binary` source exists;
- every `--hidden-import` resolves, and the runtime-critical set is declared;
- **every `PySide6.QtXxx` used in first-party code has a matching
  `--hidden-import`** — this is the big one: the exe ships a trimmed Qt, so an
  undeclared Qt import crashes only inside the packaged app, where no test runs;
- the spec is not build input, still parses, keeps its header;
- the script resolves PySide6/ffmpeg via `python -c` (stays portable).

**Mutation-checked** (I verified the tests can actually fail):
1. appended `import PySide6.QtBluetooth` to `main.py` → failed with
   "imported by the app but not bundled";
2. renamed `vendor/funasr/llama-funasr-vad.exe` → failed with "build_exe.bat
   requires these paths and they are absent".
Both mutations reverted; `git status` clean for `main.py` and `vendor/`.

Worth remembering for the `.bat` parsing: `--add-data "C:\path;dest"` contains a
colon in the drive letter, so split on the **last** `;` (`rpartition`), and the
invocation is split across lines with `^` — join those first. Guarded paths in
the script use backslashes; convert before `Path` checks.

Suite: **572 passed**.

## Packaged-exe smoke tests + a rebuild that exposed two real traps

Added `tests/test_packaged_exe_smoke.py` (14 tests) — the only check that
actually **runs** the built exe (offscreen, kill after startup, inspect
`debug.log`). It caught two genuine problems, both about *build integrity*
rather than app code:

### Trap 1 — the smoke test silently validated a STALE bundle

`dist/TranslationAgent/TranslationAgent.exe` was built Sep 10 17:39, but the
source fixes landed Sep 11 12:36. Launching it "to verify the fix" would have
exercised **old code** and passed. Encoded as `TestBuildIsCurrent`: compares the
exe mtime against every bundled first-party `.py`/`.qml`. It failed naming all
8 outdated files, exactly as designed.

### Trap 2 — an interrupted build leaves a MIXED bundle that still runs

The first rebuild (background, sandboxed) hit
`[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED]` when PyInstaller's COLLECT
stage tried `Removing dir dist/TranslationAgent` (4404 files > the 50-file
bulk-delete threshold). The removal was blocked, COLLECT died, `BUILD_EXIT=1` —
leaving **4383 files from Sep 10 and 2 from Sep 11** (Main.qml +
YouTubeVideoPanel.qml, copied before the block). The exe still launched and
every other smoke test passed.

`TestBuildIsCurrent` could NOT catch this (the exe itself was the old file, so
its mtime "matched" the old build). Added `test_bundle_is_internally_consistent`,
which buckets `_internal/**` by build *date* and fails if the newest date holds
<50% of files. Verified against a synthetic 1/21 mixed tree — it fails.

### Trap 3 — the spec banner is destroyed by every build

The rebuild regenerated `TranslationAgent.spec` from the CLI flags, wiping the
`GENERATED FILE` header. The header can't live only in the spec: by definition
a generated file loses hand-edits. Moved the warning into the build itself —
new `tools/stamp_spec_header.py`, invoked by `build_exe.bat` *after*
PyInstaller. It keeps the `# -*- coding: utf-8 -*-` declaration on line 1
(Python only honours it in the first two lines) and is idempotent.

Also had to fix `test_spec_is_not_passed_to_pyinstaller`: it asserted the
literal string `".spec"` was absent, which broke the moment the script
legitimately named the spec in the stamper call. Now it inspects the actual
PyInstaller invocation instead of a whole-file substring.

### Blocked: rebuild could not complete — C: drive is 100% full

`OSError: [Errno 28] No space left on device` mid-COLLECT. `df` shows
**238G/238G used, 0 available** — a machine-level condition, not this project's
(project is 2.6G; `gguf/` alone is 2.1G). Reclaimed ~900 MB of my own scratch
(`/tmp` 865M→330M: killed-process DLL/`.node` extracts, `ta_bundle_*`,
`ta_e2e_*`, `_MEI*`; plus `build/TranslationAgent/` intermediates, which
PyInstaller regenerates). Still only ~530M free against a ~700M build, so I
stopped rather than fill the user's system drive to the last byte.

**State:** the bundle is absent; the 14 smoke tests skip cleanly (a skip, not a
false pass). Suite: **579 passed, 14 skipped, 0 failed**. The packaged build is
therefore *declared* correct (build-contract tests, 18) but not *executed*
against current sources — needs `build_exe.bat` once there is ~1G free.

### Lesson
Verifying a build means verifying the build is *current* and *complete*, not
just that it launches. Both failure modes here produced a running exe — one
stale, one mixed — and only mtime/integrity comparisons exposed them. Never let
a rebuild's exit code go unchecked either: the first one failed and the `dist/`
tree looked plausible.

## Re-verified the format-selection fix from source (bundle still blocked)

The rebuild is blocked on disk space (`C:` 100% full; ~518M free vs ~1G needed),

**Both halves of the original report now confirmed at the bridge level:**

| scenario | selector | result |
|---|---|---|
| user picks H.264 @ 1080p (of 2160/1080/720) | `137+bestaudio` | exact 1080p, *not* the 2160p stream |
| H.264 @ 480p requested, only 2160/1080/720 exist | `""` | status "Video not available in that format/resolution." + log "This video is not available in the selected format… Choose one of the combinations listed above" |
| H.264 @ 2160p requested, only 720p exists | `""` | same refusal, names the available resolutions |

### Trap when probing QML combos from Python
`setProperty('currentIndex', n)` does **not** emit `activated(index)`, so a
probe that only sets the index sees the bridge *unchanged* (`'best'`) and looks
exactly like the original bug. That produced a false alarm mid-session. The
write-back lives in `onActivated`, so a faithful probe must set the index *and*
emit the signal:

```python
res.setProperty('currentIndex', 1)
QMetaObject.invokeMethod(res, 'activated', Qt.DirectConnection, Q_ARG(int, 1))
```

Only then does `bridge.youtubeSelectedResolution` become `'1080'` and the
selector `137+bestaudio`. **A real click does emit `activated`**, so the UI was
never broken — but any future test that sets `currentIndex` alone will report a
phantom regression.

Also note the combos start with a single placeholder entry (`count == 1`,
`currentValue == 'best'`) until an inspect completes — `youtubeResolutions` is
empty at startup, so asserting on a populated model requires pushing an inspect
first. The bridge property is `url`, not `youtubeUrl`.
