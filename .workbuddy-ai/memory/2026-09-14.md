# 2026-09-14

## Offline flow "broken after the new UI" — root cause was a truncated GGUF

**Report:** the fully offline flow (local ASR + local Hy-MT2) stopped working
after the UI migration, even though "the models are already downloaded".

**Reproduced, then fixed.** The pipeline itself was never broken: a CLI run of
the offline path on a 10 s clip completed (4 cues, rc=0). The failure only
appeared with the user's **real persisted settings**.

### Root cause chain

1. An earlier `Download ASR models` click (in the packaged app) was interrupted
   — the machine's `C:` drive was 100 % full that day — leaving
   `dist/TranslationAgent/gguf/sensevoice-small-q8.gguf` at 150,994,944 bytes
   instead of 254,208,320. `llama-funasr-sensevoice.exe` on it prints
   `gguf_init_from_reader: failed to read tensor data binary blob`.
2. `_on_models_downloaded` latched that path into QSettings
   (`asr/model = …\dist\TranslationAgent\gguf\sensevoice-small-q8.gguf`), because
   it accepted `candidate in downloaded **or** os.path.exists(candidate)`.
3. Every readiness check tested bare existence (`asrModelReady`,
   `localModelReady`, `modelsInventory`, `resolve_local_model_path`), so the UI
   showed a green tick and the offline run failed ~90 s later with
   `error: FunASR produced no transcription.`
4. `_classify_failure` then matched that line against `no (?:subtitles|transcript|caption)`
   — "no **transcript**ion" — and told the user **"No subtitles could be fetched
   for this source"** with `remedy=check_source`. The one message that could have
   pointed at the model pointed at the video instead.
5. `_ModelDownloadWorker` wrote straight to the destination, so a failed
   download left a non-empty partial file that a later run skipped as
   "already present" — the corruption was self-perpetuating.

### Fix

- **New `src/gguf_check.py`**: parses the GGUF header, metadata KV and tensor
  table via `mmap` (≈0.1–0.8 s for a 1.9 GB model, cached on
  `(abspath, size, mtime_ns)`), then requires the file to be long enough for the
  last tensor's payload — sized from its dims and GGML quantisation type.
  Detected the corrupt file to the byte: *"103213376 byte(s) short"*.
- Model state is now three-valued: `ready` / `missing` / `corrupt`
  (`localModelState`, `asrModelState`, plus `localModelProblem` /
  `asrModelProblem` for the model a run would use, and
  `…SelectionProblem` for the user's own path when a fallback masks it).
- `_ModelDownloadWorker` downloads to `<name>.part`, validates, then
  `os.replace`s; a damaged destination is repaired instead of skipped.
- `_build_run_config` never hands the CLI an unusable path — it logs
  `[warn] Ignoring --asr-model … Falling back to the models folder.` and
  auto-detects, and only raises (with repair guidance) when nothing is usable.
- `_classify_failure` gained an `ASR_MODEL` pattern **before** `SOURCE_UNAVAILABLE`
  (with `\b` added to the `no (?:subtitles|transcript|captions)` alternative so
  "transcription" can no longer match it), mapping to `REMEDY_DOWNLOAD_MODEL`.
- QML: Run and Settings now say "incomplete — re-download" and offer
  `Repair` / `Re-download ASR models` instead of a green "ready" tick.

### Verified

Through the **real QML, offscreen, with the user's real QSettings** (whose
`asr/model` still points at the corrupt file): the run now logs the
`[warn] Ignoring --asr-model … incomplete … 103213376 byte(s) short`, falls back
to `./gguf`, transcribes and translates → `statusState=done`, output written.
Also a full offline run of the user's own 4-minute video with a valid model:
rc=0, 63 cues, 9 context windows, ~17 min wall clock. Suite: **671 passed**,
1 failed — `test_packaged_exe_smoke.py::TestBuildIsCurrent`, which fails by
design until `build_exe.bat` is re-run (only 1.4 GB free on `C:`; deliberately
not attempted, matching the earlier decision not to fill the system drive).

### Traps worth remembering (also written to `.workbuddy-ai/skills/translation-agent-debug/`)

- **`HTTP_PROXY`/`HTTPS_PROXY` in the sandbox** are honoured by httpx, so
  `127.0.0.1:8081/v1/chat/completions` is proxied and returns **HTTP 404** —
  which `src/translate.py` reports as "not an OpenAI-compatible LLM server".
  It cost a full 8-minute run before the penny dropped. Clear them.
- **Port 8080 is XAMPP's Apache here**, so llama-server legitimately falls back
  to 8081. Not a bug.
- `QSettings()` is empty unless `setApplicationName`/`setOrganizationName` match
  `main.py`, so a "faithful" repro that forgets them silently tests defaults.
- A bare `except Exception: return ""` hid a real bug: `_model_status` returns a
  **2**-tuple but two new getters unpacked 3 values, so they always returned "".
  Narrow the `try` to the fallible call and log the exception.
- `cache/translation_memory.sqlite3` picked up ~70 entries from my probe runs
  (benchmark clip + the user's video). Left in place — it is the app's own cache
  and the entries are valid translations.

### Follow-up: my own `[warn]` line then poisoned the classifier

The `[warn] Ignoring --asr-model <path>: file is incomplete …` line that the fix
introduced was itself matched by the new `ASR_MODEL` pattern (the line contains
both `sensevoice…gguf` and the word "incomplete"), so **any** offline failure —
even `[error] Media file not found` — was reported as "The local transcription
model could not be used." `_classify_failure` scans newest-first and the warn
line sat directly above the real error, so it won.

Fixed by two changes:

1. `_classify_failure` drops every line starting with `[warn]` before scanning.
   Every `[warn]` in this codebase is advisory — it reports something the app
   already recovered from, so it must never drive a diagnosis. Real failures
   still arrive as `[error]`, tracebacks or raw subprocess output.
2. The `ASR_MODEL` pattern's loose
   `(?:sensevoice|fsmn[-_ ]?vad|asr)[^\n]{0,40}(?:…|incomplete|…)` alternative was
   anchored on the filename
   (`(?:sensevoice|fsmn[-_ ]?vad)[-_.\w]*\.gguf[^\n]{0,20}(?:not found|…)`) so a
   bare `--asr-model <path>` argument can never match.

**Rule to keep:** when adding a `[warn]`/advisory message, remember it lands in
the same `logText` the failure classifier reads. Name the thing you *did*, not
the thing that was wrong, or extend the skip list. Covered by
`tests/test_model_integrity.py::TestAdvisoryLinesDoNotDriveClassification`.

Final suite after this: **675 passed**, 1 failed (`TestBuildIsCurrent`).
End-to-end re-verified through the real QML with the user's real (corrupt)
persisted settings: `statusState=done`, 4 cues, `failureCode=""` — i.e. the warn
line was present and correctly did *not* produce a failure code.

### The deeper cause: the onedir move orphaned the user's models

`dist/gguf/` turned out to hold a **complete, valid** `sensevoice-small-q8.gguf`
(254,208,320 bytes, mtime 2026-08-04) and `fsmn-vad.gguf`, while
`dist/TranslationAgent/gguf/` held only the 144 MB truncated copy (mtime
2026-09-11, i.e. after the New UI commit `f6860e6`).

That dates the whole story:

1. `build_exe.bat` used to invoke
   `pyinstaller --onefile --windowed --name TranslationAgent` — a *single file*
   at `dist/TranslationAgent.exe`. So the app ran with `_base_dir()` = `dist/`
   and `_gguf_dir()` = `dist/gguf/`. The user downloaded the ASR models there on
   2026-08-04 — "we already have the models downloaded" is literally true.
2. Commit `0216a76 "fixed dl"` (2026-09-11) switched to
   `--onedir --name TranslationAgent`, so the app folder became
   `dist/TranslationAgent/` and the models folder moved with it. The Aug-4 files
   became invisible. (`--name TranslationAgent` itself is older, `9d2a21a`
   2026-07-24; it is `--onefile` → `--onedir` that moved the folder. `build_exe.bat`
   still deletes the fossil `dist\TranslationAgent.exe`.) Note this landed on the
   *same day* as `f6860e6 "New UI"` — hence the user's framing.
3. The app therefore re-downloaded the ASR models — into
   `dist/TranslationAgent/gguf/`, on a machine whose `C:` was 100 % full. That
   download was cut short; the truncated file's mtime is **2026-09-11 21:36**,
   the same day as the onedir switch.
4. Everything downstream then followed (silent green tick → `FunASR produced no
   transcription` → misread as "no subtitles").

So the user's report was accurate in every particular: it broke at the UI
migration commit, and the models *were* already downloaded — in the folder the
old onefile layout used.

**Fix.** `_model_search_dirs()` = `[_gguf_dir(), *_legacy_gguf_dirs()]`, where
`_legacy_gguf_dirs()` adds `dirname(_base_dir())/gguf` when `sys.frozen`.
`_find_model_file()` / `_find_local_model()` read through it;
`resolve_local_model_path()` gained `*extra_dirs`;
`modelsInventory` reports where a file was found and notes a broken copy that a
good one shadows; `modelsUsedText` sums both folders.

Critically, `_build_run_config` now passes `--asr-model` / `--asr-vad-model` as
resolved **absolute** paths. The CLI's own fallback
(`src/local_asr.py::_resolve_model`) is `Path(default)` and `Path("dist")/default`
— both relative to the **working directory**, which is not the app folder for a
frozen build, so merely omitting the flag would still not find the user's models.

Verified with `sys.frozen` simulated against the real tree:
`--asr-model C:\...\dist\gguf\sensevoice-small-q8.gguf`,
`--asr-vad-model C:\...\dist\gguf\fsmn-vad.gguf`, `asrModelReady=True`, and the
Models table reads
`sensevoice-small-q8.gguf | Verified | 242.4 MB · dist\gguf · broken copy in the models folder`.
So the packaged app will use the models the user already has, with **no
download** — which also sidesteps the full-disk failure that started all of this.

### Trap: the packaged-exe smoke tests can only run once per session

`tests/test_packaged_exe_smoke.py`'s module-scoped `launched` fixture deletes
`dist/TranslationAgent/debug.log` first. The sandbox **blocks that delete** and
raises `SystemExit(1)`, which aborted the module fixture and turned a single
hiccup into **9 errors** — while the first full-suite run in the session was
clean, because that run created the log the second run then tried to remove.
The fixture now falls back to truncating the file (the handler opens in append
mode, so a stale log otherwise breaks the `"Traceback" not in log` assertions).
If you see a cluster of `TestPackagedExeStarts` errors, check for that file.
