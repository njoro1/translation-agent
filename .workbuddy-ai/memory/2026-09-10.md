# 2026-09-10

## Bug: YouTube download ignored the codec/resolution dropdowns

Symptom: picking e.g. H.264 + 360p downloaded the highest-quality stream
(2160p AV1/VP9). The inspection matrix was populated correctly, so the data was
fine — the *selection* never reached the backend.

### Root cause (found by driving the real QML combos offscreen)

`AppBridge.youtubeSelectedResolution` was declared `@Property(object)`.
PySide6 registers that as `PySide::PyObjectWrapper`, which the QML engine
**refuses to write**:

```
YouTubeVideoPanel.qml:346: Error: Cannot assign int to PySide::PyObjectWrapper
```

The error only goes to the console, so the UI kept showing the pick while the
bridge stayed on its default `"best"` → highest-quality stream. The codec
dropdown worked because it is `@Property(str)`.

Debugging technique worth reusing: load `Main.qml` offscreen with a live
`AppBridge`, inject a synthetic `INFO:<gen>|{json}` payload, find the combos via
`root.findChild(QObject, <objectName>)`, then emulate a popup click with
`combo.setProperty("currentIndex", i); combo.activated.emit(i)` and read the
bridge back. The `youtubeCodecCombo` / `youtubeResolutionCombo` objectNames were
added for exactly this.

### Fixes
- `youtubeSelectedResolution` → `@Property(str)` + `normalize_resolution()`
  (collapses int / JS double / str to `"720"` / `"best"`).
- `youtubeResolutions` now emits **string** values so the model and the stored
  selection are the same type.
- QML pickers use `valueRole` + `indexOfValue()` instead of hand-rolled `===`
  loops over mixed int/string values.
- `resolve_video_option()` is **strict**: exact (codec, height) or `None`. The
  old "closest height" substitution is gone.
- New `describe_unavailable()` builds the user-facing message ("This video is
  not available in H.264 at 480p. Available …: 1080p, 720p, 360p."); surfaced
  as `youtubeSelectionError`.
- `_selected_format_selector()` no longer falls back to `bv*+ba/b`; an empty
  selection makes `downloadYouTubeVideo()` refuse with a clear message.
- `_YouTubeDownloadWorker` takes `expect={codec,height,cap}` and verifies the
  produced file with ffprobe (best-effort, reports a `[warn]` on mismatch).
- `translate.py::_video_selector_for` mirrors the strict behaviour (raises).
- `LogDrawer.qml`: `Accessible.CheckableMenuItem` is not exposed in QML →
  `Accessible.CheckBox`.

### Verification
New `tests/test_youtube_format_selection.py` drives the real QML combos.
Full suite: **512 passed**.

### Test-infra note
`Main.qml` must only be loaded **once** per pytest process. A second
`QQmlApplicationEngine` loading it intermittently segfaults inside
`engine.load()` (access violation) — `engine.deleteLater()` is only processed
while an event loop runs, and offscreen pytest never spins one. Use the
session-scoped `qml_main` fixture in `tests/conftest.py` (it also snapshots
load-time warnings so later tests can mutate the bridge safely).

### Lesson
In PySide6, never use `@Property(object)` for a property QML writes to — it
becomes unwritable. Use a concrete type (`str`, `int`, `bool`, `float`) and
normalise in the setter.

## Live-network validation (`_probe_youtube.py`)

Ran against a real 4K/60fps video (Big Buck Bunny, AV1 + VP9 + H.264, 8 heights)
through the *exact* bridge path. Result: `RESULT: ALL SELECTIONS RESOLVED`.

- 34 (codec, resolution) pairs the UI can offer → every one resolves to an exact
  pinned format-id selector, e.g. h264/360p → `230+bestaudio/...`, not a range.
- `youtubeResolutions` is **codec-aware**: H.264 stops at 1080p, AV1/VP9 go to
  2160p. The dropdown never offers a hole — verified programmatically.
- The 2 genuinely-absent pairs (H.264 @ 2160p / 1440p) are refused with
  "This video is not available in H.264 at 2160p. Available H.264 resolutions:
  1080p, 720p, 480p, 360p, 240p, 144p."

Probe gotchas (both cost a false-failure round):
1. Read `b.youtubeResolutions` **after** setting the codec — the list changes.
2. `_on_youtube_info` drops payloads whose tag mismatches, so bump
   `b._youtube_info_gen` and prefix `f"INFO:{gen}|"` *after* setting `b.url`.
3. Never hard-code "144p is unavailable" — many videos really serve it. Derive
   the missing pairs from the matrix (cartesian product minus what exists).

Environment: yt-dlp 2026.08.19 present; **ffprobe is NOT on PATH**, so the
post-download `_verify()` check silently no-ops here (returns `None`).

## Follow-up 1: made the post-download verification actually run

`_verify()` was dead code in practice — it called `probe_video_file()`, which
only used **ffprobe**, and ffprobe is not installed. `ffmpeg` *is* available
(`imageio_ffmpeg`, already a dependency for merging), but that wheel ships no
ffprobe.

- `probe_video_file()` now tries ffprobe first, then falls back to
  `ffmpeg -hide_banner -i <file>` and parses the `Stream #0:0 … Video: h264 …
  426x240` line off **stderr**. Note `ffmpeg -i` with no output exits non-zero
  by design, so the return code is deliberately ignored (`_probe_via_ffmpeg`).
- Shared `_run_probe()` helper + `_FFMPEG_STREAM_RE`; `_probe_result()` maps
  codec names through `_FFPROBE_FAMILY`.

**Bug found while wiring this up:** `_option_best_height()` stores
`"codec": "best"`, so `_selected_expectation()` produced `codec="best"` for
"Best (any)" + a resolution, and `_verify()` compared that literal against the
real codec → *every* such download warned "codec H.264 instead of Best".
Fixed with `any_codec = cap or want_codec in ("", "best")` — codec is only
compared for an explicit codec pick.

## Follow-up 2: end-to-end proof (`_e2e_download.py`)

Real download, real file check (not just the selector string):
`python _e2e_download.py [url] [codec] [res]` →
wanted `h264 @ 240p`, got `h264 @ 240p` (426x240, 19.5 MB) → **PASS**.
This also proved the ffmpeg fallback probe works (ffprobe was `None`).

Suite now **529 passed** (was 512): +9 `TestProbeVideoFile`, +8
`TestDownloadVerification`.

### Lesson
A verification step that silently no-ops is worse than none — it reads as
"checked" while checking nothing. Also: a wrong warning is worse than no
warning, so give "any/auto" selections an explicit exemption before comparing
them to a concrete value.

## Follow-up 3: the UI really does show the message (`_verify_ui_message.py`)

The backend *produced* the right text; nothing had checked the QML *rendered*
it. `_verify_ui_message.py` loads `Main.qml` offscreen with a synthetic 5-format
payload and reads the live properties:

| case | observed |
|---|---|
| H.264 / 720p | `Selected: 720p · H.264 · mp4 · 30fps · video + audio merge` (theme text colour) |
| H.264 / 2160p | `This video is not available in H.264 at 2160p. Available H.264 resolutions: 1080p, 720p, 360p.` (warning colour) |
| Download pressed | status carries the same `[error]`, **no worker started** |
| back to 360p | returns to `Selected: …` |

## Follow-up 4: SectionPanel layout warning

`SectionPanel.qml` put `anchors.fill: parent` on a `MouseArea` that was a child
of a `RowLayout` — undefined behaviour, and Qt warned 8× per app start
("Detected anchors on an item that is managed by a layout"). Fixed by wrapping
the header `RowLayout` in a plain `Item` (`Layout.preferredHeight:
header.implicitHeight`) with the click target filling that. **Warnings: 8 → 0.**

Suite now **533 passed**. Screenshot: `ui_shots/youtube_message_check.png`.

### Screenshot note
To grab a QML window you must `from PySide6.QtQuick import QQuickWindow` at
**module level, before** `rootObjects()` — otherwise the root comes back as a
plain `QWindow` and `grabWindow()` does not exist.
